
# 🎤 ianAutoKTV 智慧開源 KTV 系統

ianAutoKTV 是一個基於 Python 與 Web 技術打造的區域網路 KTV 系統。只需輸入 YouTube 網址，系統便會自動下載影片，並利用 AI 模型（Spleeter）將「原唱」與「伴奏」音軌分離，最後透過網頁介面提供專業的 KTV 點歌與播放體驗。

無論是用電視大螢幕播放、手機掃碼遙控，還是用筆電單機歡唱，ianAutoKTV 都能完美支援！

---

## ✨ 核心特色

* **🤖 AI 智慧去人聲**：內建 Spleeter 引擎，一鍵將 YouTube 影片轉換為包含原聲、導唱、伴奏三種模式的 KTV 伴唱帶。
* **📱 手機掃碼遙控器**：無需安裝 App，手機掃描 QR Code 即可化身點歌機，支援搜尋、切歌、音量控制。
* **🎛️ 即時原聲/導唱/伴奏與升降 KEY**：透過 Web Audio API，在播放中切換六聲道音訊中的三組立體聲，並依瀏覽器環境使用 SoundTouch AudioWorklet 或 HTTP LAN 相容的 Tone.js fallback。
* **📺 多螢幕聯動支援**：
    * `播放端`：適合放在客廳電視或第二螢幕全螢幕顯示。
    * `遙控端`：適合多支手機同時連線點歌。
    * `一體機`：適合單台電腦或平板，左半邊看 MV、右半邊點歌。
* **📦 綠色免安裝架構**：支援 PyInstaller 打包，可製作成隨身碟帶著走的免安裝版（Portable）。

## 🚀 系統架構與運作原理

1.  **下載階段**：使用 `yt-dlp` 優先下載 H.264/AVC、最高 1080p 的 YouTube 影音，降低舊型電腦以 CPU 軟解 AV1 或 4K 影片造成的播放負擔。
2.  **處理階段**：透過 FFmpeg 將音訊轉出，交由 AI 模型 `spleeter:2stems` 產生人聲與樂器分離音軌。
3.  **合成階段**：依 v1.0.4 已驗證的固定規則建立三組立體聲：原聲直接使用下載檔案的原始音軌；伴奏直接使用 Spleeter `accompaniment.wav`；導唱使用小聲人聲與正常音量伴奏混合。六個 mono 聲道會以 FFmpeg `amerge` 封裝為 v1.0.4 相容的 `5.1` 配置，避免後續 `6.0/join` 聲道語意造成導唱與伴奏左右聲道錯位；響度處理目標為 `-14 LUFS` 與 `-1 dBTP`，實際結果仍依來源與 AAC 編碼而異。最後與原畫質影像封裝為 `.mp4`，聲道 1-2 為原聲、3-4 為導唱、5-6 為伴奏。播放時導唱只採用 c2，並將同一訊號複製至左右喇叭，不使用可能含低頻或錯位內容的 c3。
4.  **驗證階段**：FFprobe 會檢查輸出 MP4 的第一條音訊流必須是 6 channels；驗證失敗時不會視為製作成功。
5.  **播放階段**：Flask + SocketIO 建立的輕量級伺服器，負責串流影片並同步所有連線裝置的指令。

### AI 音訊格式與舊歌曲相容性

新製作歌曲只產生一個 MP4，內含一條六聲道音訊流。播放器使用 `ChannelSplitter(6)` 將三組立體聲分流：原聲使用第 1-2 聲道、導唱使用第 3-4 聲道、伴奏使用第 5-6 聲道。伺服器在播放事件中以 FFprobe 傳送實際聲道數，播放器不依賴 Chrome 的 `MediaElementAudioSourceNode.channelCount` 推測格式，並使用離散聲道解讀。這種設計避免播放時啟動 FFmpeg，適合 AMD A8-3870 與 8 GB RAM 的舊型電腦。

既有舊歌曲仍使用兩聲道格式，播放器會依音訊聲道數自動使用相容模式：原唱取左聲道，伴奏取右聲道；導唱按鈕在舊歌曲上會播放兩聲道混合內容。管理端的「既有影片 AI 去人聲」也會直接將輸入影片轉換成同樣的六聲道單一 MP4，不會增加歌曲檔案數量。

## 🌐 介面導覽

* **/player**：播放器端。請在客廳電視或外接螢幕的瀏覽器開啟，雙擊即可進入全螢幕。
* **/remote**：遙控器端。請用手機瀏覽器開啟，頁面頂端固定顯示分頁列；進入「點歌」分頁時，搜尋欄與分類篩選列也會固定在分頁列下方，以分頁區分「點歌」與「實際遙控」：點歌分頁負責搜尋、分類篩選與加入待播清單；實際遙控分頁負責查看待播清單、暫停/繼續、切歌、切換原聲/導唱/伴奏、音量、升降 KEY、字幕與播放端 QR Code。切換回點歌分頁時會保留離開前的歌曲列表捲軸位置。
* **/admin**：管理後台。負責貼上 YouTube 網址來製作新歌，並提供系統底層日誌監控。
* **/combo**：雙合一控制台。適合使用單台寬螢幕電腦遊玩，同時整合播放、控制與點歌介面；歌曲列表由遙控區外層捲動容器管理，避免在小螢幕高度下被 flex 佈局壓縮而無法顯示。
* **/soundtouch-prototype**：SoundTouch/WSOLA 音訊處理驗證頁，供測試音高、播放同步與瀏覽器相容性。

管理後台的「批量新增 KTV 歌曲」可在文字區每行輸入一首歌曲，格式為 `YouTube 網址 | 歌名`。送出後由伺服器沿用單曲製作流程逐首執行，包含 Spleeter 分離、原聲/導唱/伴奏三組固定分類、六聲道封裝與響度平衡，並共用「製作完成後自動平衡歌曲音量」勾選狀態；每首歌曲的原聲是原始音軌，導唱是小聲人聲加正常伴奏，伴奏是正常音量的 Spleeter accompaniment，三者均以 `-14 LUFS / -1 dBTP` 為目標。批量處理不會同時啟動多個 Spleeter 工作；單首失敗會記錄日誌並繼續下一首，最後統計成功與失敗數量。批量處理期間系統會維持忙碌鎖，避免其他下載或更新工作與 AI 分離同時執行。

管理後台進階區的「手動製作歌詞檔」可選擇既有歌曲並播放，先在文字區一次貼上完整歌詞（每行一句），按「建立歌詞行」後，在播放過程中對指定歌詞行按「加入時間碼」；已加入的時間碼可按「移除時間碼」重新記錄。儲存時會依時間排序已標記的歌詞行，寫入與歌曲同名的 VTT；未加入時間碼的行不會輸出。最後一句若未手動結束，會使用歌曲總長度作為結束時間，歌詞時間不可重疊，儲存前由後端再次驗證。

遙控器與一體機的選歌列表支援分類篩選。符合 `歌曲名稱-主唱者名稱-語言-編號.mp4` 命名規則的歌曲，可依歌曲名稱字數、主唱者歌手與語言篩選；不符合規則的舊歌曲會歸入「未辨識」，仍可使用文字搜尋。遙控器 `/remote` 以固定置頂的前端分頁區隔點歌與實際遙控；點歌分頁的搜尋與分類工具列固定在分頁列下方，切換回點歌分頁時還原先前捲軸位置；待播清單位於實際遙控分頁，分頁切換只控制顯示面板，不改變既有 SocketIO 控制事件；點擊「播歌」後，按鈕會暫時顯示「已加入」並停用，歌曲列也會短暫高亮，避免重複點擊。

播放端與一體機播放畫面預設在右下角顯示遙控器 QR Code，手機掃描後會開啟同一台主機的 `/remote`；遙控器頁面可使用「顯示播放端 QR Code」開關，同步控制所有播放端與一體機的 QR Code 顯示狀態。開始播放歌曲時，兩個播放畫面會在中央顯示不含 `.mp4` 附檔名的歌曲名稱約 10 秒，之後自動淡出；成功加入待播清單時，播放區上方會顯示不含附檔名的新增檔案名稱約 5 秒。

播放端與一體機的「音訊引擎」狀態列會顯示目前模式的整曲平均 LUFS。播放開始時分析原聲；按下原聲、導唱或伴奏時，伺服器會以 FFmpeg `ebur128` 分析該模式對應的聲道並回傳一次結果，畫面不會持續跳動。六聲道合成時會先對三種最終立體聲分別套用 `-14 LUFS / -1 dBTP`，再以 v1.0.4 相容的 `amerge/5.1` 封裝，避免 `6.0/join` 聲道語意造成導唱右聲道被當成低頻聲道或左右聲道自動錯位，也避免多次 AAC 重編碼造成雜訊。播放端會將 MediaElementAudioSourceNode 設為六聲道離散輸出；模式切換會先取消舊聲道的排程並明確歸零，再啟用新聲道；六聲道輸出會將每組左右聲道分別送至對應的左右輸出，避免左右訊號重複相加造成音量變大。
播放端與一體機在第一首歌建立 Web Audio 音訊圖期間，會先暫存收到的模式、音量與 KEY 控制，待音訊圖完成後套用，避免首首歌的控制指令因初始化競態被忽略。

播放器啟動音效上下文時不會預先建立 MediaElementAudioSourceNode；收到播放事件後，必須先等待影片 `loadedmetadata` 確認實際聲道數，再建立 Web Audio 音訊圖並開始播放。這可避免六聲道歌曲在媒體 metadata 尚未載入時以瀏覽器預設雙聲道建立來源，造成 c4/c5 伴奏通道不可聞。`player.html` 與 `combo.html` 均遵循相同時序：metadata -> 建立六聲道離散分流 -> 套用目前模式 -> 播放。

播放畫面下方的音訊狀態列也會顯示歌曲實際聲道模式，例如 `5.1`，並顯示 Web Audio 實際聲道數與目前啟用通道（例如導唱 `WebAudio：6ch/explicit｜啟用：c2`、伴奏 `啟用：c4,c5`）；此資訊由播放事件中的 FFprobe `channel_layout` 與播放器 runtime 提供。六聲道歌曲在影片 metadata 載入後，播放端會將 MediaElementAudioSourceNode 設為 `explicit/6`，再交給離散 ChannelSplitter 分流，避免音訊圖在待機初始化時只有 2 聲道而使 `c4/c5` 伴奏失效。導唱 c2 會同時接到 merger 左右輸出，c3 不參與播放。一體機按鈕會先立即套用本機模式，再透過 SocketIO 同步其他播放端；伺服器的模式切換也會先廣播聲道變更，再於背景分析整曲 LUFS，避免 FFmpeg 分析期間阻塞切歌控制。

### 字幕流程

後台的「新增 KTV 歌曲」流程只輸入 YouTube 網址與歌名，不會自動產生字幕檔，也不會在歌曲完成後建立同名 VTT。若要加入字幕，請使用系統日誌下方預設收合的進階「既有歌曲歌詞轉檔」卡片，選擇既有 `.mp4` 與 `.srt`、`.lrc` 或 `.vtt` 字幕檔，或直接貼上字幕文字；系統會依檔案副檔名或文字內容自動判斷格式並儲存同名 VTT。字幕轉檔失敗時，後端會回傳 HTTP 錯誤狀態與詳細錯誤訊息，管理後台會明確顯示「轉檔失敗」而不會誤顯示成功。`/player` 與 `/combo` 使用 HTML5 `<track>` 載入 WebVTT cue，再由播放畫面的自訂 KTV 渲染器顯示字幕：最多顯示兩行並以畫面中央為對齊基準，第一行位於中央左側且文字右對齊，第二行位於中央右側且文字左對齊；只有一行時自動置中，並固定在影片接近底部的位置。每個字會帶有短暫放大彈跳動畫，但不使用卡拉 OK 變色或填色效果。遙控器與一體機的「播放中」控制區可切換字幕顯示，並同步設定小字 80%、標準 100%、大字 120% 三種字幕大小；伺服器會將設定廣播至所有播放畫面，並同步更新控制端的目前選取狀態。字幕關閉時會清除自訂渲染內容並停用顯示。

目前專案尚未內建 Whisper 或其他 AI 語音辨識模型；自動歌詞辨識屬於下一階段的後端處理流程，應由音訊抽取、AI 轉錄、逐字時間戳正規化與 VTT 儲存組成，完成後即可直接餵給上述 KTV 渲染器，不需要修改播放端。

前端模板由 Flask/Jinja 渲染；內嵌 JavaScript 的 JSDoc 型別請避免使用未跳脫的 `{{...}}` 物件型別寫法，以免被誤判為 Jinja 表達式而造成頁面 500 錯誤。

### 為什麼以 VTT 作為儲存與播放格式

SRT 適合人工製作與交換，LRC 適合歌詞同步，VTT 則是 HTML5 `<track>` 的瀏覽器原生格式。統一儲存為 VTT 可以直接交給 `<track>`，不必在每台播放裝置重複轉換，也能使用 WebVTT 的語言、標籤與顯示設定；因此系統接受三種輸入格式，但在伺服器端統一轉成 VTT。這不是說 SRT 或 LRC 不好，而是 VTT 更符合本系統的瀏覽器播放管線。

### 播放效能與舊型電腦

播放端會經過 Chrome 與 Web Audio 音訊分流；在 AMD A8-3870 這類不具 AV1 硬體解碼的舊型平台，4K AV1 或高解析度 AV1 歌曲可能由 CPU 軟體解碼而造成 LAG。系統下載新歌時會優先選擇 H.264/AVC、最高 1080p，以提高硬體解碼機會；既有的 AV1/4K 歌曲仍需使用 FFmpeg 轉成 H.264/1080p 後再播放，避免在瀏覽器播放時即時轉檔。

管理端系統日誌下方的「進階」卡片現在分成四個獨立且預設收合的功能：既有歌曲歌詞轉檔、既有影片效能最佳化、既有影片 AI 去人聲，以及既有歌曲音訊平衡。影片效能最佳化會以 FFmpeg 重新編碼為 H.264、最高 1080p，並重新編碼音訊套用共同的 `-14 LUFS / -1 dBTP`；系統日誌會依序顯示接收檔案、FFmpeg 執行、輸出檔大小、取代原 MP4 與最終成功或失敗結果；成功條件包含 FFmpeg 回傳碼正常、輸出檔案存在且檔案大小大於 0，成功後才取代原 MP4。Windows 會以 UTF-8 並容錯讀取 FFmpeg 輸出，避免系統 cp950 解碼例外。音訊平衡同樣套用 `-14 LUFS / -1 dBTP`，影片畫面直接複製；歌詞轉檔、手動歌詞與系統維護只處理字幕或系統檔案，不涉及音訊。四個工具互不共用輸入欄位，且高負載處理工作不能同時執行。

新增 KTV 歌曲時可勾選「製作完成後自動平衡歌曲音量」，系統會在合成音訊時對原聲、導唱與伴奏分別套用 FFmpeg `loudnorm`，以 `-14 LUFS` 與 `-1 dBTP` 作為共同目標，減少不同歌曲之間的音量落差。這個處理發生在製作階段，不會增加播放時的 CPU 負擔。既有歌曲必須重新執行管理端的音訊平衡工具，才會套用新的基準。

若不使用管理端 UI，也可以用腳本最佳化單首既有歌曲（會在成功後取代原 MP4，並重新編碼音訊套用 `-14 LUFS / -1 dBTP`）：

```powershell
.\optimize_existing_video.ps1 -InputFile ".\ktv_songs\我甘願重新愛過-洋蔥 Feat.狗柏.mp4"
```

這個最佳化腳本是伺服器外的維護工具，會重新編碼音訊並套用 `-14 LUFS / -1 dBTP`，不會在播放時執行；完整主程式包與一般更新包都會附帶此腳本。若只新增或修改此腳本，既有安裝不需要重新打包 EXE；若修改 `main.py` 的下載策略，則既有安裝仍需使用一般 `build_update.ps1` 更新包。

## ⚠️ 注意事項

* **版權聲明**：本專案僅供程式交流與個人家庭娛樂使用，請勿將下載之版權影音用於任何商業行為。
* **硬體需求**：AI 去人聲（Spleeter）會消耗一定的 CPU/記憶體資源，處理一首 4 分鐘的歌曲約需 1~3 分鐘不等，請耐心等候。
* **升降 KEY**：播放服務現在以自簽 HTTPS 啟動，播放端使用 SoundTouch AudioWorklet。每台裝置第一次連線需先接受憑證警告；若仍使用舊的 `http://192.168.x.x` 網址，瀏覽器會無法啟用 AudioWorklet。
* `yt-dlp.exe` 必須使用官方獨立執行檔，不要使用 `.venv\Scripts\yt-dlp.exe` 這類可能綁定舊 Python 路徑的 launcher，否則下載歌曲時會回報 Code 1。
* 程式啟動時不會載入 TensorFlow；只有開始下載並處理歌曲時才會載入 Spleeter。若處理歌曲時仍出現 TensorFlow DLL 錯誤，請確認使用完整主程式包，且不要只替換 exe。
* 若啟動時出現 `Failed to load the native Tensorflow runtime`，請使用同一次建置產生的完整主程式包與更新包，不要只替換 exe。
* 若啟動時出現 `Invalid async_mode specified`，請重新執行 `build_release.ps1` 與 `build_update.ps1`，使用新產生的完整資料夾；打包設定已固定使用 `threading` 並納入 Engine.IO driver。
* 若下載成功、只有「AI 去人聲」出現 `DLL 初始化例行程序失敗`，表示程式已啟動，問題通常在使用者電腦的 TensorFlow 執行環境。請先安裝 Microsoft Visual C++ 2015-2022 Redistributable x64，確認 Windows 為 64 位元且 CPU 支援 AVX，再重新測試。若仍失敗，請提供使用者電腦的 CPU 型號與 Windows 版本。
